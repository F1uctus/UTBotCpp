# Что ещё не проверено в Windows-порте UTBotCpp

Этот список относится к ветке `ci/portable-utbot-fixes` и дополняет отчёт
[`WINDOWS_PORT_CHANGES_RU.md`](WINDOWS_PORT_CHANGES_RU.md). Пункт в этом файле
не означает известную поломку: он означает, что для сценария пока нет
воспроизводимого успешного теста.

## Реальное устройство и firmware

- [ ] Полная сборка embedded firmware ARM-компилятором.
- [ ] Сборка проекта в IAR Embedded Workbench. Этот этап сознательно отложен.
- [ ] Прошивка микроконтроллера и запуск сгенерированных тестов на плате.
- [ ] Проверка startup-кода, linker script, секций памяти и векторов прерываний.
- [ ] Работа с реальными периферийными устройствами, таймерами, DMA, watchdog,
  прерываниями и RTOS.
- [ ] Совместная работа host-сгенерированных входных данных и аппаратного
  test harness.

Сейчас полноценно исполняется переносимая C/C++ логика на Windows-host. Код,
который напрямую обращается к регистрам MCU или зависит от аппаратных событий,
нуждается в стабах, модели периферии, симуляторе или реальном устройстве.

## Полнота проверки проектов

- [ ] Генерация тестов для всего embedded-проекта, а не только выбранного
  переносимого модуля.
- [ ] Большой C++ проект с классами, шаблонами, исключениями и сложными
  зависимостями заголовков. Текущий CI smoke test использует два простых C-файла.
- [ ] Проекты с несколькими библиотеками, несколькими целями и DLL.
- [ ] 32-битные Windows-проекты и другие архитектуры. Артефакт сейчас только
  `x86-64`.
- [ ] Автоматическое получение `compile_commands.json` и `link_commands.json`
  из Visual Studio/MSBuild, CMake и других build system. В CI эти базы создаются
  контролируемым скриптом.
- [ ] Масштабирование на полном крупном проекте: время, память и стабильность
  многочасовой генерации.

## Генерация и выполнение тестов

- [ ] Компиляция и запуск сгенерированных GoogleTests непосредственно в Windows
  GitHub Actions. Workflow пока проверяет наличие файлов и число тестовых
  случаев; локально синтетические и ISO5-тесты компилировались и проходили.
- [ ] Полный набор unit/integration tests самого UTBotCpp на Windows. В workflow
  используется `ENABLE_UNIT_TESTS=OFF`.
- [ ] Покрытие нескольких исходных файлов и всего проекта в CI. Для ISO5
  покрытие измерялось локально, но не является отдельным CI gate.
- [ ] Обработка аварий, тайм-аутов, нехватки памяти и частично созданных KLEE
  output для большого набора разных функций.
- [ ] Параллельная генерация и одновременная работа нескольких пользователей.

## Сервер и клиенты

- [ ] Подключение VS Code plugin к нативному Windows gRPC-серверу.
- [ ] Подключение CLion plugin и полный пользовательский сценарий из IDE.
- [ ] Реальный gRPC-запрос на reflection endpoint. Библиотека reflection
  собирается и линкуется, но CI проверяет CLI и генерацию напрямую.
- [ ] Долговременный запуск server mode, повторные запросы и корректное
  завершение дочерних процессов.

## Переносимость артефакта

- [ ] Ручная загрузка ZIP на другой физический компьютер с Windows 10 и
  Windows 11 без Visual Studio, LLVM, Python и vcpkg.
- [ ] Пути с пробелами, кириллицей и длиной, близкой к ограничениям Windows.
- [ ] Файловые системы без поддержки hard link. Ошибка `latest.log` не должна
  останавливать работу, но этот сценарий отдельно не воспроизводился.
- [ ] Проверка Windows Defender, SmartScreen и антивирусами сторонних
  производителей.
- [ ] Подпись `utbot.exe` и DLL. Текущий CI-артефакт не подписан.

Relocation-тест GitHub Actions уже переносит пакет в новый каталог, очищает
`UTBOT_ALL` и ограничивает `PATH`. Это подтверждает отсутствие зависимости от
build tree, но не полностью заменяет тест на отдельном чистом компьютере.

## Другие платформы и совместимость

- [ ] Linux unit tests после общих изменений логгера и поиска программ в
  `PATH`. Windows workflow не запускает Linux-матрицу.
- [ ] macOS: эта ветка её не собирает и не тестирует.
- [ ] Совместимость с другими версиями LLVM/KLEE. Текущая связка закреплена на
  LLVM 22.1.8.
- [ ] Обновление baseline vcpkg и версий gRPC/Protobuf. Сейчас они намеренно
  закреплены для воспроизводимости.

## Известные ограничения текущего результата

- Без Python подробные временные показатели `klee-stats.py` недоступны;
  генерация работает, но соответствующие значения статистики равны нулю.
- Windows-пакет KLEE основан на upstream KLEE. Недоступные опции UTBot KLEE fork
  отбрасываются адаптером, поэтому результаты некоторых сложных сценариев могут
  быть уже, чем на Linux с оригинальным fork.
- Архив GitHub Actions хранится 30 дней и должен быть скачан или опубликован
  отдельно, если нужен постоянный релиз.

## Рекомендуемый порядок следующих проверок

1. Скачать artifact на чистый Windows 10/11 и повторить smoke fixture.
2. Добавить в Windows CI сборку и запуск сгенерированных GoogleTests.
3. Проверить запуск gRPC server и подключение одного IDE-клиента.
4. Расширить host-тест с одного переносимого модуля до нескольких независимых
   модулей.
5. После возвращения к аппаратной части настроить ARM/IAR-сборку, симулятор и
   выполнение на плате.
